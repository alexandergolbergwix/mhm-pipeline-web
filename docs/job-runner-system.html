1The one-paragraph mental model

A job is a Postgres row. The API creates the row and spawns an asyncio task in the web process itself; the task heartbeats progress into the row and cooperatively honours a cancel flag; startup hooks reap stale rows and respawn interrupted ones. The frontend never trusts memory — it polls the row (globally for the job tray, per-job when a page is attached, or in a waitForRunJob loop when code needs to await), with WebSocket pushes merged in purely to make progress feel instant. The 409-on-duplicate-start is the glue that lets any tab attach to an already-running job instead of erroring.

2Big-picture architecture

Everything lives in two processes: the browser and the FastAPI dyno. Postgres holds the truth; the WebSocket channel is a latency optimisation only.

Why no Celery / queue?

The job volume is "one curator clicked a button", not "thousands of tasks per second". A Postgres row + in-process asyncio task gives durable state, restart recovery, and progress reporting with zero extra infrastructure — the same Postgres already backs the app.

3Job status lifecycle

Statuses: queued running succeeded failed cancelled. The first two are "active" — only one active job per (run_id, kind) may exist.

5Kind dispatch & the worker contract

_execute_job() in run_job_service.py is a plain if/elif dispatcher over 9 job kinds. Every worker follows the same contract.

The worker contract (what every run_*_job does)

# the shape every job worker follows (see verify_job.py)
async for event in work_stream:
    if await is_cancel_requested(job_id):        # ① cooperative cancel
        await finish_job(job_id, status=CANCELLED, ...)
        return
    await update_job_progress(job_id, {          # ② heartbeat + UI progress
        "phase": "running", "processed": n, "total": total,
        "message": "...", "session_id": sid,
    })
await finish_job(job_id, status=SUCCEEDED,       # ③ terminal write
                 result={...}, progress={"phase": "done", ...})

update_job_progress ≙ heartbeat

Every progress write bumps updated_at (server-side onupdate=func.now()). That timestamp is what fail_stale_jobs() checks — so a worker that reports progress is, by definition, alive.

6Cooperative cancellation

Cancel never kills a task. It stamps a flag; the worker notices it at the next loop iteration and shuts down cleanly (closing its stream, writing a proper terminal status).

7Crash & restart resilience

Heroku recycles dynos daily. The in-memory asyncio tasks die with the process — but the rows don't. Two startup hooks in the FastAPI lifespan repair the world:

fail_stale_jobs()

Any running row whose updated_at heartbeat is older than 20 minutes is marked failed with a human-readable "the server restarted" error. Prevents the UI from polling a zombie forever.

recover_interrupted_jobs()

Every remaining queued/running row gets spawn_job() called again — the job restarts on the fresh process instead of being lost.

8The frontend: three layers, one truth

All three layers poll at the same 2-second cadence; the WebSocket merges snapshots in early, but the next poll always wins.

9waitForRunJob.ts — the awaitable flavour, line by line

Hooks give you state; sometimes code just needs to wait. This module is ~100 lines of exactly that.

export async function waitForRunJob(runId, jobId, opts) {
  const deadline = Date.now() + (opts?.timeoutMs ?? 20 * 60_000); // matches backend stale cutoff
  while (Date.now() < deadline) {
    const job = await RunJobs.get(runId, jobId);   // poll the row
    opts?.onUpdate?.(job);                         // stream progress text to the UI
    if (job.status === "succeeded") return job;    // resolve
    if (job.status === "failed" || job.status === "cancelled")
      throw new Error(job.error ?? `Job ${job.status}`);
    await sleep(2_000);                            // same 2s cadence as the hooks
  }
  throw new Error("Background job timed out — try Cancel and start again.");
}

12Caveats & design notes

In-process workers share the event loop

A heavy job competes with request handling on the same dyno. CPU-bound work belongs in Modal (extraction already does this); new job kinds should stay I/O-bound or offload.

Horizontal scaling caveat

With multiple dynos, every dyno runs recover_interrupted_jobs() at startup and could re-spawn the same row. Fine at 1 web dyno (current setup); would need a claim/lock column before scaling out.

Why results embed snapshots

Verify jobs write a session_snapshot into result (Rule W-33): session GETs must work even when a different dyno — with a different /tmp — serves the request. The row is the only shared storage.

One active job per (run_id, kind)

This invariant is what makes everything composable: the 409 is deterministic, "attach" is always unambiguous, and the UI never has to disambiguate competing jobs of the same kind.
